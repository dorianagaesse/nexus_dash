# ND-374 realtime load test

Date: 2026-10-06
Task: ND-374 (Retire legacy SSE routes and load-test realtime fallback behavior)
Branch: `refactor/nd-374-retire-sse-routes`

## Change under test

The branch deletes the legacy SSE routes
(`app/api/projects/[projectId]/activity/stream`, `app/api/account/notifications/stream`)
and their stream libraries. The client transport is broadcast with a bounded
adaptive polling demotion when the broadcast provider is unavailable; in
polling transport mode the client uses the same leader-coordinated pollers.
`REALTIME_TRANSPORT` accepts `broadcast` or `polling`; the legacy `stream`
value fails startup validation.

## Harness

`scripts/load-test-realtime.mjs` creates one owner and one member user with
sessions in the target database, opens one owner tab and `LOAD_TEST_USER_TABS`
member tabs against the target server, then over `LOAD_TEST_DURATION_MS`:

- renames the project twice through the API (a mid-run rename and a final
  rename after a tab reload), recording the expected snapshot version
  (`project.updatedAt`) for each;
- asserts transport-level version delivery: at least one polling tab must
  observe a `/activity` response carrying the expected version after each
  rename;
- asserts per-tab poll bounds (`ceil(elapsed / interval) + 3` per tab, activity
  10 s / notifications 20 s), leader-coordinated member totals, zero SSE
  requests on every tab including the owner, and readable activity snapshots;
- cross-checks the server metrics snapshot (`/api/observability/realtime`):
  `activity.snapshotChecks` must not exceed observed polls; in broadcast mode
  observed polls must be attributed as `activity.pollingFallbacks`; in polling
  mode no realtime tokens may be minted and no websockets may open;
- records DOM convergence (tabs showing the renamed name) as telemetry, not as
  an assertion — see the refresh-cancel observation below;
- deletes its fixture users on exit.

## Recorded runs

Both runs used a local production build (`next start`) against an isolated
local PostgreSQL database, 3 member tabs plus the owner tab, 60 s configured
duration.

### Polling transport (`REALTIME_TRANSPORT=polling`)

Elapsed 73.3 s. Member activity polls: 6 / 0 / 5 (11 total against an
independent-tab volume of 33 and a leader-only bound of 14). Owner tab: 8
activity polls, 4 notification polls. All 20 assertions passed.

| Metric | Value |
| --- | ---: |
| Elapsed | 73,264 ms |
| Activity polls (member total / owner) | 11 / 8 |
| Notification polls (member total / owner) | 5 / 4 |
| `activity.snapshotChecks` | 19 (observed polls: 19) |
| `notifications.snapshotChecks` | 9 |
| `activity.pollingFallbacks` | 0 |
| Realtime token requests / websocket opens | 0 / 0 |
| Legacy SSE requests (all tabs) | 0 |
| Database query delta | 2,246 |

Server timing: `project.activity.poll` 19 calls, 329 ms total, 87.8 ms max;
`account.notifications.poll` 9 calls, 259.7 ms total, 101.8 ms max. A poll
snapshot check costs one indexed `Project.updatedAt` read; the database work
stays proportional to poll volume, and poll volume stays at one tab's cadence
regardless of tab count.

### Broadcast transport with provider outage

The server ran with `REALTIME_TRANSPORT=broadcast` and an unreachable provider
URL, so token minting succeeds but channel joins fail and every tab must
demote to bounded polling. Elapsed 74.2 s. Member activity polls: 5 / 0 / 5
(10 total, bound 14); owner 8. All 20 assertions passed.

| Metric | Value |
| --- | ---: |
| Elapsed | 74,209 ms |
| Activity polls (member total / owner) | 10 / 8 |
| Notification polls (member total / owner) | 6 / 4 |
| `activity.snapshotChecks` | 18 (observed polls: 18) |
| `notifications.snapshotChecks` | 10 |
| `activity.pollingFallbacks` | 18 (observed polls: 18) |
| Realtime tokens issued / denied | 8 / 0 |
| Websocket connection attempts | 9 (all failed, as intended) |
| Legacy SSE requests (all tabs) | 0 |
| Database query delta | 2,264 |

Every poll observed under the outage was attributed as a fallback, so the
fallback counters fully account for demand generated by the outage. The same
bounds held as in polling mode: outage demotion does not change the polling
cadence or the leader coordination.

### Convergence telemetry

Both runs recorded 3/3 member tabs showing the renamed project name at both
rename phases, and both version-delivery assertions passed (observed by the
tab holding activity-poll leadership at the time; leadership moved across
reloads).

## Acceptance mapping

- No legacy SSE invocations: tabs request no SSE endpoints locally, and the
  routes are deleted in this branch. Confirming "no legacy SSE invocations" in
  Vercel Observability requires a deployment of this branch — that check
  belongs to the post-merge Production broadcast rollout verification.
- No continuous server function activity from idle tabs: idle tabs make only
  bounded periodic polls (5-6 activity polls and 0-6 notification polls in
  ~74 s against 10 s / 20 s cadences) and stream nothing.
- Bounded database and function growth per active user: poll volume is flat
  per project scope regardless of tab count (leader coordination), each poll
  performs one indexed version read, and the outage path adds no extra polls.

## Observations outside this branch

- **RSC refresh-cancel flake (pre-existing, transport-independent).** In a
  single-tab diagnostic harness, the client-initiated `router.refresh()` RSC
  fetch was canceled client-side (`net::ERR_ABORTED`, CDP `canceled: true`)
  shortly after starting in most runs, leaving that tab stale; a buffered
  interception of the same response made the refresh apply every time. The
  production client fetch path (Next 16.2.7 `fetch-server-response.js`) passes
  no abort signal, and the behavior reproduces headed and headless. It is a
  pre-existing ND-373 client path, not introduced by this branch; both
  recorded multi-tab runs above converged 3/3. Follow-up candidate if it is
  seen in the field.
- **Local server CPU spin (single occurrence, not reproduced).** One local
  `next start` process froze near 100% CPU during harness iteration; a
  database probe showed idle connections and no locks. A cleanly restarted
  server passed every subsequent run; neither recorded run above was
  affected.

## How to run against Preview

Confirm `/api/health/ready` reports the revision of the intended commit (the
preview alias is last-deploy-wins), then:

```bash
vercel env pull .env.preview.local --environment=preview
LOAD_TEST_BASE_URL=https://<stable-preview-alias> \
MIGRATION_DATABASE_URL=<preview database url> \
LOAD_TEST_USER_TABS=3 LOAD_TEST_DURATION_MS=60000 \
LOAD_TEST_LABEL=preview LOAD_TEST_OUTPUT=.tmp/load-test-preview.json \
node scripts/load-test-realtime.mjs
```

The harness needs database access to create and remove its fixture users;
prefer a non-production database.
